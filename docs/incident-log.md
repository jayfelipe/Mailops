INC-001 — DER walk read content-start where it needed the sibling offset
Symptom: 4 test failures. rsa_modulus_bits raised "expected BIT STRING"on structurally valid RSA keys; downstream, check_record reported validkeys as "not valid base64".Diagnosis: DER is tag-length-value. After reading a TLV, its contentstart (i) and its end (end) are different pointers: enter a container ati, skip to the next sibling at end. The outer walk entered instead ofskipping after the AlgorithmIdentifier, landing on the OID inside it(byte 6) instead of the BIT STRING (byte 19). The fixture repr in the testoutput showed the 0x03 sitting right where the code wasn't looking.Fix: Second walk step jumps to the algid's end. Also split base64decoding from DER parsing in check_record — one ValueError was beingmapped to "invalid base64" regardless of which layer actually failed.Lesson: (1) In TLV formats, "where content begins" and "where the nextthing lives" are different pointers. (2) Error messages must name the layerthat failed, or they send the responder looking at the wrong component.(3) A passing test can pass for the wrong reason — test_testing_mode_flaggedwas green because t=y is evaluated before key parsing, not because thekey path worked.

INC-002 — worker auth failure: a Postgres answered, but it wasn't ours
Symptom: first host-side TCP connection to localhost:5432 rejected with"password authentication failed for user mailops". Every docker compose exec db psql operation had worked all session.Diagnosis: [lo que mostró netstat/tasklist]Fix: [puerto remapeado a 5433 / volumen reinicializado]Lesson: (1) exec runs inside the container over the unix socket withtrust auth — it never exercises the published port or password auth, so itcan mask a broken TCP path all session. Test the real path early.(2) PostgreSQL returns the same FATAL for wrong-password and unknown-user,so the message alone can't tell you WHICH server answered — identify thelistener (netstat/tasklist) before touching config. (3) POSTGRES_* env varsonly seed an empty volume; they silently don't apply to existing ones.

INC-003 — db "unhealthy" during crash recovery; api/worker refused to start
Date: 2026-10-14Symptom: docker compose up -d failed after ~103s: "dependency failedto start: container mailops-db-1 is unhealthy". db logs showed a scary wallof FATAL lines.Diagnosis: Log timeline showed the previous container was killeduncleanly ("shutdown was interrupted"), so on start Postgres ran crashrecovery — 70+ seconds of data-directory fsync on a slow Windows/WSL2 disk,then WAL redo. The FATAL lines were the healthcheck's own pg_isready probes(5s apart, matching the configured interval) being rejected during recovery.Postgres finished recovering and went healthy on its own; compose's waitwindow expired first. Config was never broken.Fix: stop_grace_period: 30s on db (clean shutdowns avoid the recoveryin the first place) + start_period: 60s on the healthcheck (don't countfailures while the database is still booting).Lesson: (1) "unhealthy" does not mean broken — it means "not ready",and crash recovery legitimately isn't. (2) FATAL connection rejectionsduring startup are normal Postgres behavior; matching the FATAL timestampsto the healthcheck interval identified them as probes, not failures.(3) For the second time, depends_on: service_healthy refused to stackservices on top of a database that wasn't accepting connections — payingfor itself again.
